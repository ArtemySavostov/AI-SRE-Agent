# SSH connection и Docker discovery

Backend подключается к Linux-хосту по SSH-ключу и читает сведения о хосте и Docker.
Удалённых установок, `sudo`, перезапуска контейнеров и изменения demo нет.
Сервисы, добавленные вручную, не изменяются: найденные контейнеры пока отдельный
инвентарь, который позднее можно связать с ManagedService.

## Подготовленный demo

- Доступ с Mac: `git@localhost:2522`.
- Для backend в Docker Desktop: `git@host.docker.internal:2522`.
- Отдельный ключ: `.local/ssh/demo_ed25519` (публичная часть уже добавлена на demo).
- Параметры подключения: `.local/demo-connection.json`.
- Приватный ключ и локальные настройки исключены из Git и Docker build context.

Сохраняется SHA256-отпечаток host key, проверенный по уже известному SSH-хосту.
Это отпечаток **сервера**, не созданного клиентского ключа. При замене сервера
нужно сверить новый ключ по доверенному каналу и явно обновить настройку.
При переносе проекта на другую машину ключи не копируются через Git: перенеси
их защищённым способом либо создай новый ключ и установи его публичную часть.

## Запуск backend в текущем Compose

Из корня `/Users/artemy/ai-agent`:

```bash
docker compose -f compose.yaml -f backend/sre-platform/compose.ssh.yaml config --quiet
docker compose -f compose.yaml -f backend/sre-platform/compose.ssh.yaml up -d --build backend
python3 backend/sre-platform/scripts/configure-demo.py
```

Используй оба Compose-файла при последующих пересозданиях backend: второй
монтирует каталог ключей read-only и задаёт путь внутри контейнера.
`localhost` внутри backend-контейнера относится к самому backend, поэтому
скрипт по умолчанию использует подготовленный `host.docker.internal`.
Этот адрес подходит для Docker Desktop на Mac; при переносе backend на Ubuntu
укажи реально доступный адрес demo-хоста и его SSH-порт.

Скрипт запросит email и пароль **учётной записи SRE-платформы**. Он не запрашивает
SSH-пароль. Учётная запись должна уже существовать; скрипт не создаёт пользователей.
Затем можно выбрать существующие проект/сервер либо явно выбрать создание demo-записей.
Скрипт получает CSRF-токены и работает через обычную сессию приложения.
Пароли не сохраняются в файлах и аргументах командной строки.

Если backend запущен локально из IDE:

```bash
python3 scripts/configure-demo.py --host localhost
```

Для повторного запуска без выбора:

```bash
python3 scripts/configure-demo.py --email your@email.example \
  --project-id PROJECT_UUID --server-id SERVER_UUID
```

`--url` задаёт адрес backend, если опубликованный порт отличается от 8080.
Скрипт задаёт SSH-настройки, выполняет тест, запускает сбор и показывает результат.
Frontend-формы настройки SSH пока не добавлены.

## API

Все адреса начинаются с `/api/project/{projectId}/server/{serverId}`.
Требуются авторизованная сессия и CSRF-токен для изменяющих запросов.
Сервер проверяется на принадлежность указанному проекту. Модель доступа остаётся
существующей в приложении: авторизованные пользователи работают с общими проектами.

| Метод | Путь | Ответ |
|---|---|---|
| PUT | `/ssh` | Сохранённые настройки, без приватного ключа |
| GET | `/ssh` | Настройки подключения |
| POST | `/ssh/test` | Проверка SSH и чтения Linux-хоста; Docker проверяет discovery |
| POST | `/discovery` | `202`, jobId и Location для опроса |
| GET | `/discovery` | Последняя задача и последний успешный снимок |

Пример PUT `/ssh`:

```json
{
  "host": "host.docker.internal",
  "port": 2522,
  "username": "git",
  "credentialId": "demo_ed25519",
  "hostKeyFingerprint": "SHA256:ЗАМЕНИ_НА_ПРОВЕРЕННЫЙ_ОТПЕЧАТОК_СЕРВЕРА"
}
```

`credentialId` — имя файла в `SRE_SSH_KEYS_DIRECTORY`; абсолютные пути, `..` и
символические ссылки за пределы каталога запрещены. Используется отдельный
ключ без парольной фразы, защищённый правами файла. Приватный ключ не передаётся
через API и не сохраняется в БД. Пользователь SSH должен иметь доступ к Docker
socket; приложение не меняет его права. Доступ к обычному Docker socket даёт
широкие привилегии на хосте, поэтому ключ предназначен для доверенной платформы.

## Содержимое снимка

- `host`: hostname, ОС, ядро, архитектура, число CPU, память, uptime.
- `docker`: версия, имя хоста Docker, storage driver, число контейнеров.
- `containers`: полный container ID, имя, image, state, health, Compose project/service,
  время запуска, порты и IP в Docker-сетях.
- `collectedAt`: время успешного сбора на backend.

ENV, секреты Docker, содержимое файлов и произвольные labels не собираются.
Docker state и health остаются отдельными значениями: `running` не означает,
что приложение здорово, а отсутствие healthcheck представляется `null`.
Снимок заменяется только после полного успешного сбора. Если контейнер исчез
между `docker ps` и `inspect`, весь сбор считается неуспешным: повтори его.
При успехе без контейнеров сохраняется пустой список; это не ошибка соединения.

## Задачи и ошибки

Состояния: `QUEUED`, `RUNNING`, `SUCCEEDED`, `FAILED`. В `FAILED` возвращаются
безопасные `errorCode`/`error`; старый снимок остаётся доступен, ориентируйся
на его `collectedAt`, чтобы понять возраст данных.

Одновременно работают 2 discovery-задачи, очередь — 16. На одном сервере
разрешён только один сбор; повторный запуск или изменение SSH во время сбора
возвращает `409`. Проверка SSH ограничена общим пулом из 4 соединений.
Общий срок SSH-операции — 60 секунд; connect timeout — 10 секунд.
Лимиты: 1000 контейнеров, до 4 MiB stdout и 64 KiB stderr на команду.

`HOST_KEY_REJECTED` — неверный отпечаток; `AUTH_FAILED` — ключ или пользователь;
`KEY_UNAVAILABLE` — отсутствует mount/файл ключа; `REMOTE_COMMAND_FAILED` —
Docker недоступен, нет прав, контейнер исчез при сборе или превышен лимит;
`TIMEOUT` — истекло время; `QUEUE_FULL` — очередь заполнена.

Текущая очередь рассчитана на **один экземпляр backend**. После перезапуска
незаконченные задачи отмечаются `FAILED/RESTARTED`; снимки сохраняются.
Периодический сбор и история всех запусков пока не добавлены: запуск ручной,
хранится последняя задача и последний успешный снимок для каждого сервера.

## Схема БД

Добавлены `server_ssh_connection` и `server_discovery`; существующие таблицы
и модель ManagedService не менялись. В текущем dev Compose используется
`SPRING_JPA_HIBERNATE_DDL_AUTO=update`, новые таблицы создадутся при старте.
Для окружения с `validate` есть [SQL](sql/ssh-discovery.sql), который нужно
применить к существующей SRE-БД через принятый механизм миграций. Это не полный
baseline схемы и не автоматическая Flyway-миграция: в проекте пока нет baseline
для остальных сущностей. Не включай Flyway на существующей схеме без его настройки.

## Проверки

Unit/API-тесты (API использует H2 в памяти в PostgreSQL mode, без Docker):

```bash
./mvnw -Dtest=DiscoveryTests,DiscoveryStoreTests,DiscoveryApiIntegrationTests,InfrastructureServiceTests test
```

Отдельная read-only проверка реального demo-хоста:

```bash
SRE_SSH_INTEGRATION=true \
SRE_DEMO_FINGERPRINT='SHA256:ПРОВЕРЕННЫЙ_ОТПЕЧАТОК' \
./mvnw -Dtest=SshDemoIntegrationTests test
```

H2-тесты проверяют API, JPA и сохранение снимков, но не заменяют проверку
миграций и блокировок на PostgreSQL. Проверка реального SSH читает сведения
demo-сервера и отдельно убеждается, что неверный отпечаток отвергается.
